## Context

Implementation-specific functionality is built into the core repository today:
Java in the WAR, React pages in the single bundle, Liquibase changesets in the
core changelog, menu rows and permission keys in core seeds. The design document
records the evidence (35 implementation-named commits on `develop`, an
1,839-line `App.jsx`, 174 hand-listed entity classes, dozens of feature toggles)
and the consequences: core grows with every implementation, one implementation's
feature can regress another, and implementation teams cannot develop, test,
version or deploy their own functionality independently.

The design document compares five backend models and four frontend models
(section 7) and reconciles them with the companion comparison _OpenELIS
Modularization Plan: Comparing Architecture Models_ (Ian Bacher, internal
review, 2026-10-28). This record states the decision and settles the open
questions the design left to Phase 0 (section 25.2) so that Phase 1 can start.

## Decision

OpenELIS Global gets a **manifest-driven module system**: one artifact type, a
module JAR described by `META-INF/openelis-module.json`, in two shapes
(`provider`: extension-point implementations only; `module`: beans, REST
controllers under `/rest/modules/<id>/`, JPA entities, a Liquibase changelog,
permissions, menu entries and a prebuilt frontend remote). Modules are
discovered at application start from `/var/lib/openelis-global/modules`, each
loaded by its own **parent-first class loader** and wired into its own **child
Spring context** whose parent is the core root context. The React application
becomes an **application shell** that reads `/rest/module-registry`, registers
module routes behind the existing `SecureRoute` gate and lazy-loads module
bundles from the same origin. Inside the core, ArchUnit rules with a frozen
baseline keep feature boundaries from eroding.

Models considered and set aside (design section 7): convention-only classpath
scanning (no identity, no compatibility, no migrations), module-first class
loading (two copies of a framework in one JVM), module beans in the root context
(a module could replace or advise core beans), out-of-process modules (no shared
session or transaction; kept for integrations such as the Analyzer Bridge),
general-purpose plugin frameworks (PF4J, OSGi, JPMS layers: thin Spring
integration, repackaging of the core, nothing for the frontend), a
library-assembled core (sites without Java developers would have to build their
own server) and, on the frontend, build-time integration, single-spa and plain
import maps (kept as the fallback loader).

### Decisions on the open questions (design section 25.2)

| #   | Question                                                                                                         | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Reasoning                                                                                                                                                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Publishing of `openelis-spi`, `openelis-module-api`, `openelis-core` classes, the BOM and `@openelis/module-sdk` | Built by the core build and installed to the local Maven repository (`mvn install`) and the frontend workspace; a module repository's CI checks out the core at the tag named in its `requires.openelis` and installs it before building. Publication to a remote repository (GitHub Packages for Maven and npm) is a Phase 5 operations item.                                                                                                                  | No remote repository exists for the project's artifacts today (the `dataexport` submodule follows the same local-install pattern); a module can be built and tested without waiting for a publishing pipeline.                                                                                                |
| 2   | Package naming                                                                                                   | Every module class lives under `org.openelisglobal.module.<name>`: `backend.basePackages`, the activator, the entities and the extension classes. The sub-packages the core owns (`api`, `manifest`, `runtime`, `web`, `testkit`) are reserved and the validator refuses any other package.                                                                                                                                                                     | One namespace for everything that is a module keeps module classes recognizable in logs, stack traces and the coupling report, and a child context can only ever scan `org.openelisglobal.module.<name>`, never a core package; module JARs stay off the webapp class path, so the core scan never sees them. |
| 3   | Strict mode default                                                                                              | Opt-in. A `modules.lock` digest allowlist is honoured when present and refused JARs are `INVALID`; a deployment without the file runs every JAR in the directory.                                                                                                                                                                                                                                                                                               | Installation already requires filesystem access to the deployment checkout, which is the trust boundary; strict mode is an additional control sites can switch on.                                                                                                                                            |
| 4   | Core access policy for providers                                                                                 | Report, do not refuse. The registry's core-coupling report lists which of the three core artifacts a module references; the template keeps `openelis-core` out of a provider's dependencies.                                                                                                                                                                                                                                                                    | A refusal would turn a packaging mistake into a start-up failure for a working provider.                                                                                                                                                                                                                      |
| 5   | Schema layout                                                                                                    | Module tables and sequences live in the `clinlims` schema with the mandatory prefix `mod_<id>_` (hyphens replaced by underscores).                                                                                                                                                                                                                                                                                                                              | One schema keeps backups, the existing JNDI datasource and the Liquibase `databasechangelog` table unchanged; the prefix makes module objects recognisable and removable.                                                                                                                                     |
| 6   | Uninstall data policy                                                                                            | Retain tables and permission rows when a module is removed.                                                                                                                                                                                                                                                                                                                                                                                                     | Follow-up and audit data must survive an operator removing a JAR; a module may ship an uninstall changelog for an administrator to run explicitly.                                                                                                                                                            |
| 7   | Route policy                                                                                                     | Module routes live under `/m/<id>/` only (admin pages under `/admin/m/<id>/`). Top-level paths are not accepted in this version.                                                                                                                                                                                                                                                                                                                                | Core routes are still JSX in `App.jsx`, not data, so a top-level module path cannot be checked for collisions; the prefix makes a collision impossible. Allowing top-level paths once core routes are data is an additive change.                                                                             |
| 8   | Phase 6 candidate                                                                                                | The **Specimen Follow-up & Action Tracker** module, developed in its own repository (`mozzy11/openelis-module-specimen-followup`), is the first module-native workflow and the proof of the architecture: it owns its tables, reuses `PatientService`, the sample services and the user directory, contributes a `Samples` menu entry and its pages, and ships a complete create, list, detail, update and delete workflow. OGC-1144 remains a later candidate. | A workflow that references existing patients and specimens without touching core tables exercises every contract the design names (discovery, migrations, permissions, menu, routes, core-service reuse, authorisation) on a real screen flow.                                                                |
| 9   | Governance                                                                                                       | New extension points, facades and extension slots are added by core pull request, reviewed by the core maintainers; the exposed core UI index and the slot catalogue are listed in the SDK changelog.                                                                                                                                                                                                                                                           | Same review path as every other core change.                                                                                                                                                                                                                                                                  |

| 13  | Decision record sign-off                                                                                         | The core maintainers sign this record through the pull request that merges it; the community may review it on the forum once the `modula` branch is proposed for `develop`.                                                                                                                                                                                                                                                                                     | Keeps the record in the same review flow as the code.                                                                                                                                                                                                                                                         |
| 14  | Loader engine                                                                                                    | The design's own parent-first `URLClassLoader` subclass. PF4J is not adopted.                                                                                                                                                                                                                                                                                                                                                                                   | A few hundred lines of JDK code with no second framework to keep in step with Spring; PF4J's default is plugin-first and its Spring bridge is thin.                                                                                                                                                           |

## Consequences

- A module can ship a complete workflow (schema, services, REST API, pages,
  navigation, permissions) without a core pull request, built and versioned in
  its own repository against three published core artifacts.
- The core never sees module beans; only declared extensions, controllers under
  the module path and forwarded events cross the boundary. A module cannot
  replace or advise a core bean.
- Modules are trusted code with the application's privileges. There is no
  sandbox; installation is a file operation in the deployment checkout followed
  by a restart.
- Every module declares the minimum OpenELIS version it was built against; a
  module the running version cannot satisfy is reported and skipped.
- With no modules installed, start-up and behaviour are unchanged; the module
  runtime is verified by its own tests and by the example module the core CI
  loads.
- Module tables, permission keys, message keys, menu ids, REST paths and routes
  all derive from the module id, which keeps every namespace rule mechanical.
- The core takes on new maintenance: the SPI and module API versioning, the
  exposed core UI index, the slot catalogue and the ArchUnit baseline.

The work lands on the `modula` branch in one pull request per phase
([OGC-1578](https://uwdigi.atlassian.net/browse/OGC-1578) contracts,
[OGC-1579](https://uwdigi.atlassian.net/browse/OGC-1579) backend runtime,

([OGC-1583](https://uwdigi.atlassian.net/browse/OGC-1583)) developed outside the
core against that branch. `modula` is proposed for `develop` once the module
workflow runs end to end on it.
