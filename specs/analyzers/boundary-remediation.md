# Analyzer boundary remediation: interpret once

Decision date: 22 October 2026. Status: follow-up cleanup in progress; the current cleanup inventory supersedes earlier completion claims.

The user directed an audit of duplicated decisions and a simpler boundary: the Bridge decides what the instrument reported once; OpenELIS handles its own laboratory responsibilities. This supersedes the decimal-setting-in-every-bundle proposal and its blanket historical-reprocessing requirement.

Audited source: OpenELIS `fde241e1a6892f1e4ff6851766e1f48814c4cc79`, Bridge `b8618f9ad562f1ec270419909396b388b9950120`. Scope: Bridge receipt, routing, parsing, rendering, outbox and retry; OpenELIS bundle validation, mapping defaults/editor, confirmation, activation, adoption, import, held recovery, placement and QC routing. This is a source audit, not a production incident or frequency assessment. The table records the pre-cleanup audit; current implementation and validation are summarized in [final remediation](final-remediation.md).

For the numbered work list, owners and reasons, start with the [cleanup inventory](cleanup-inventory.md).

## Decision

**Interpret once in the Bridge; deliver the preserved outcome; map and place it in OpenELIS.**

The Bridge owns sender resolution, instrument protocol and file decoding, aliases and connection code overrides, number format, vendor translations, record/component extraction, control recognition, failure recognition and informational flags. OpenELIS must not reconstruct those decisions from a currently served profile or current connection settings when importing or recovering an already interpreted result.

OpenELIS owns the approved mapping to its local catalog, enabled assays and exclusions, valid local targets, patient/sample/order placement, operational QC targets and calculations, review, acceptance, audit and duplicate prevention. The Bridge currently has profile terminology/defaults, not the lab-approved mapping to OpenELIS test/component/answer IDs. Do not replicate that local catalog and approval workflow into the Bridge.

Both systems validate their boundary: the Bridge validates instrument input; OpenELIS validates the delivered contract, authenticated sender, local connection association, supported types and coherent fields. Those are not duplicate parsing. OpenELIS must reject contradictory or malformed delivered values, not blindly trust arbitrary JSON because its sender is paired.

## Required bundle contract

The versioned FHIR contract and executable Bridge/OE fixtures document the replacement after deletion of the duplicated gates. Reuse existing FHIR fields where their meaning is sufficient; add only missing semantics. Exact extension/schema changes belong to that implementation contract, not an ad hoc list of duplicated profile fields.

A delivered result must identify its source connection/message and specimen; its interpreted test and component identities; its typed value, comparator and units; canonical qualitative answer when known; patient/control classification; failed-run versus result versus informational outcome; and original instrument text as audit evidence. Carry standard codings where the profile supplies them. A stable profile-defined identity is permitted where no standard code exists; unknown input must remain explicitly unresolved. A raw string alone must not claim that two different semantic results are the same test. Never invent a standard code or infer clinical equivalence from a display label. Canonical identities are stable within their profile across parser revisions. Apply the current approved local binding, including deliberate corrections; previous target equality is not required. A different profile scope remains unresolved until an appropriate binding exists. A genuinely different source meaning requires a new identity.

Do not ship the entire parser recipe to OE for re-execution or equality gating. Historical profile/configuration evidence can remain with the Bridge audit record and bundle provenance without participating in OE acceptance. A decimal-setting field is not required for OpenELIS to consume a valid numeric quantity.

Example: the Bridge interprets a comma-formatted number and a translated qualitative answer, then delivers numeric `1.23` and the canonical answer identity, with the raw text preserved. OE chooses the approved local test and answer option and the matching sample/order. Changing either input language or number format afterward cannot change or block this bundle. Changing the local target mapping is a separate audited lab action and may require confirmation before local recovery.

## Implemented boundary and remaining acceptance

The user-directed execution order was deletion first, replacement tests second, and remaining contract/local-validation gaps third. The following groups describe the final responsibilities, not approval prerequisites.

1. **Contract and fixtures — Bridge + OE.** Inventory existing emitted fields for ASTM, HL7, FILE and HTTP tabular traffic. Define the smallest versioned normalized result contract and supported old/new combinations. Add producer/consumer fixtures for quantity, call, combined number/call, components, control, failure, flags and unknown values. Do not assume existing qualitative payloads are already complete.
2. **Bridge normalization and durable receipt.** Canonicalize aliases/translations/part roles consistently; validate numeric grammar rather than guessing commas/thousands. Preserve an immutable decoding context at receipt and final bundle at rendering. Test interruption after durable receipt but before rendering, concurrent settings edits, restart and ordinary retry. FILE's retained context is useful existing behavior, not proof that other transports have it. Keep local mapping IDs out of Bridge.
3. **OE local-only import and recovery.** Consume delivered identities/typed outcomes; retain local approvals, catalog compatibility, exclusions, placement, QC, receipts and audit. Remove calls that rebuild historical readings from live profiles/connections. Replace `AnalyzerRecordReading`/`AnalyzerArrivalReading` gating and recognition hash gating; keep any historical columns read-only for audit until a documented cleanup migration. No permanent dual interpretation path.
4. **Setup, adoption and UI.** Separate configuration review from local mapping approval in editor, type status and activation. Map canonical answers only; raw vendor text remains audit evidence. Allow operators to remove obsolete spelling rows without making them runtime acceptance gates. Retain stale-editor guards and real local target changes. Update labels and tests so parser edits no longer advertise mapping invalidation.
5. **Existing data and mixed versions.** Classify old bundles by semantic completeness, not age or absent decimal metadata. Numeric quantities and already explicit outcomes need no raw-message reprocessing. For incomplete qualitative meanings, preserve original payload and use retained historical evidence or an explicit reviewed mapping decision; do not reconstruct from today's profile as historical fact. Recover accepted held rows in place; retain receipts, dismissed/finalized records and audit. Never mass rewrite finalized results or invent a new delivery ID. A general raw-message reprocessor is deferred unless a demonstrated unrecoverable payload requires it.
6. **Validate, push, reconcile reviews.** Test the matrix below, run the repository CI workflow using `oe-fix-ci`, push both stack tips with `gh stack`, and pin the Bridge implementation in OE. Reply to and resolve the two open delivery findings only after the replacement behavior is implemented and proved. User retains dependency merges; update pins to actual upstream merged commits afterward. No merge or deployment is authorized by this plan.

### Regression matrix

- Render once, change each parsing-only setting family in the inventory, deliver/retry: identical values/classification/identity, no OE re-interpretation hold and no live Bridge catalog/connection read during import or held recovery.
- Receive raw data, interrupt before rendering, edit settings, restart: original retained interpretation context wins; FILE and non-FILE covered.
- Unknown source/ambiguous input: explicit unresolved outcome, no guess; wrong connection or contradictory classification/value rejected.
- Receive before local mapping confirmation, then confirm: local recovery succeeds without parser snapshots; real mapping changes remain reviewable and audited.
- Translated calls, non-English calls beside numbers, aliases, multi-part results, excluded answers, unknown answers: same canonical meaning across protocols; raw text remains visible.
- Changed profile ID/revision, reused code with different meaning, inaccessible catalog, missing optional historical metadata: no whole-profile gate; genuine incompatible meaning cannot silently map.
- Failure versus other absent value, control versus patient, flags versus calls, comparator and units: preserve distinct outcomes and local safeguards.
- Lost acknowledgement, concurrent duplicate delivery, recovery of an already accepted held result, dismissed result, finalized result: no duplication or unintended rewriting.
- Adoption/activation/editor: parsing-only edits do not invalidate local mapping; local target/exclusion edits still require approval; configuration authorization and validation remain.
- Mixed versions and existing mapping rows: supported combinations documented/tested, conflicting translation decisions surfaced, missing semantics handled explicitly without new blanket holds.

## Scope and release status

This needs coordinated Bridge and OE changes, not a PNG-only workaround. Mock fixtures may change to prove the contract; no new mock runtime responsibility is introduced. Offline installation, deployed PNG migration, a general reprocessing console, replicating the local catalog into Bridge and unrelated certificate work are outside this boundary remediation.

Baseline `fde241e1a6` passed all 16 local CI groups (9,203 backend tests, zero failures/errors, nine skipped). On the audit refresh its GitHub checks have no non-passing entries except the expected trusted upstream-pin validation. These results establish the earlier baseline, not cleanup acceptance. The reviewed findings have since been fixed, replied to and resolved. Complete validation on the final candidate remains required; see [final remediation](final-remediation.md). Dependency merges remain the user's action.
