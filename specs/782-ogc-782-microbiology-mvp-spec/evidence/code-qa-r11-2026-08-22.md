# Code QA - R11 Culture Purpose

## Scope

Applied the repository-pinned `tools/code-qa` alignment, meaningful coverage,
simplicity, and evidence checks to the active Culture purpose roadmap slice.

## Result

**Aligned and narrowly scoped.** A microbiology order now carries an explicit
purpose: Clinical diagnosis/treatment or Active screening/carriage. New orders
visibly default to clinical purpose, historical missing values remain visible
as Unspecified, pre-release corrections are audited from the previous value to
the new value, and final cases remain read-only.

WHONET preview and CSV generation use the same purpose selection. Clinical
records are included by default; screening and unspecified records each require
their own explicit inclusion control. Both controls persist in the canonical
page address and the completed export selection.

This follows the OpenELIS Work M-09 requirement to include screening and
surveillance cultures explicitly without inferring purpose from program names,
specimen, organism, patient origin, or location. OpenELIS Work does not prescribe
where that classification is stored; the feature specification's explicit
order-level Culture purpose is the product ruling for this slice.

## Meaningful Coverage

- Service and integration tests cover required new-order purpose, historical
  null compatibility, audited pre-release correction, final-case locking,
  filtering, preview counts, generation, and persisted selection.
- The Liquibase integration test applies, rolls back, and reapplies the nullable
  Culture purpose column.
- Frontend component tests cover the visible order default, Unspecified display,
  correction controls, audit rendering, final read-only behavior, independent
  WHONET controls, and canonical query serialization.
- The registered `core-app` Playwright journey corrects a case purpose,
  verifies the timeline, exercises both WHONET controls independently, checks
  preview counts, verifies a final case is locked, and includes a 390-pixel
  viewport overflow check. It uses Carbon labels and roles with no forced
  actions or arbitrary waits.

Focused validation passed 53 backend tests, 44 frontend tests, the two-case R11
Playwright journey, and seven adjacent order-entry and WHONET journeys.

## Visual Check

Desktop and mobile evidence was inspected for the order detail, case summary,
timeline audit, final-case lock, and WHONET configuration states. The touched

layout patterns and preserve the compact M-09 configure-and-preview intent.

## Simplicity

**Verdict: lean.** The slice adds one nullable persisted classification and two
independent query booleans because the historical and screening populations are
behaviorally distinct. It reuses the existing order-detail service, case
activity timeline, final mutation guard, WHONET query and selection pipeline,
Carbon components, and service-created fixture endpoint. No program-name
heuristic, parallel reporting path, new workflow engine, or production fixture
data was introduced.
