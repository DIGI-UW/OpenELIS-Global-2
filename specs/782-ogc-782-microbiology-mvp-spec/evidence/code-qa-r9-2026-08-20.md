# Code QA - R9 WHONET Population Filters

## Scope

Applied the repository-pinned `tools/code-qa` meaningful coverage, spec/code
alignment, and simplicity checks to the M-09 existing-data filter slice.

## Result

**Aligned and appropriately scoped.** Preview and CSV generation use the same
normalized server-side compiler for reporting period, specimen, organism,
patient origin, significance, and de-duplication. The filter controls use
Carbon components, round-trip through canonical repeated query parameters, and
the single Reports navigation entry preserves `/Microbiology/whonet`. Completed
exports retain that normalized population selection as typed JSON so their
provenance does not depend on reconstructing a request later.

The implementation intentionally does not infer screening or surveillance from
program, origin, specimen, organism, or location. The next roadmap slice
captures Culture purpose explicitly as clinical diagnosis/treatment or active
screening/carriage, with historical missing values shown as Unspecified.

The deployed validation also exposed and fixed a null-data defect that was not
specific to the filter controls: a valid finalized culture may contain an
isolate that has not yet been identified. Filter options and preview now omit
that unidentified isolate from organism mapping without failing the reporting
period.

## Coverage

- Seventeen focused JUnit 4 dataset-service cases verify combined filters,
  period-scoped options, request binding,
  report-service delegation, incomplete historical reference labels, the
  service-created filter fixture, unidentified isolates, and empty periods.
- Integration tests verify JSONB selection round-tripping and Liquibase update
  and rollback behavior. The migration is the only data-model change in this
  slice.
- Vitest/RTL verifies canonical URL compatibility, deterministic query
  serialization, and keyboard/role interactions with the Carbon filters.
- The deployed registered `core-app` run passed shared authentication and both
  functional journeys (3/3 total). It selects the service-created specimen,
  both organisms, inpatient origin, and both significance values; reloads the
  canonical URL; previews the same population; follows mapping repair links;
  and generates the CSV without arbitrary waits or forced actions.
- The registered `core-demo-video` run passed shared authentication plus the
  desktop and mobile R9 stories (3/3 total). Five screenshots and two titled
  MP4s were generated through the pinned evidence bundler.
- Desktop and mobile Configure, Preview, and Generate frames were visually
  inspected against the authoritative OpenELIS Work M-09 mock. Reports
  placement, export parameters, preview funnel, mapping warning, and generation
  align for this slice. Export History, scheduling, worklist and case entry
  points, advanced first-isolate options, and additional mapping domains remain
  explicit later roadmap rows.

## Simplicity

**Verdict: lean.** The implementation extends the existing WHONET compiler,
service, export-run record, worklist context query, route, and Carbon page. The
batch context query removes per-case loading; the typed selection object is
used by both generation and persisted provenance. The dedicated
`WHONET_FILTERS` scenario is property-gated and reuses the reviewed-AST service
fixture instead of duplicating AST setup in deployment shell.

The functional and demo suites now share one WHONET Playwright helper for
canonical query construction, supported Carbon multi-select interaction,
readiness checks, fixture labels, and CSV reading. The extraction removed the
second local copy instead of adding another test abstraction.

## Guardrails

The one schema change has a Liquibase rollback. Fixtures use authenticated
application services only: no SQL seed, fixed primary key, DAO bypass, or
production fixture exposure. No duplicate export route, client-side source of
truth, screening inference, scheduling abstraction, or speculative mapping
store was introduced. Network waits synchronize named API operations, and
Carbon multi-selects are closed through their supported keyboard interaction.

The isolated stack still reports unrelated analyzer-menu duplicate-key and
missing-translation warnings. They predate and do not originate in this slice,
so they are flagged for the analyzer surface rather than patched here.

The external Review button overlaps one mobile filter in full-page evidence.
That chrome is injected by review tooling; OpenELIS itself has no page-level
horizontal overflow. It remains a review-tooling presentation issue and was not
hidden with application or evidence-only CSS.

The live AMR checklist contains the separate `AMR-S30` R9 story with five
required reviewer steps. Its preview expectation uses the deterministic
post-filter counts and explicitly allows the unfiltered totals to include other
stories that share the demo reporting date.
